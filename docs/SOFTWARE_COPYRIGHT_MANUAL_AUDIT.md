## 截图来源与结算矛盾

旧脚本运行的是V1.0.1生产Web构建，画面由实际引擎渲染，但取图过程直接修改了运行状态：

- 初始化写入已解锁20关和部分已完成引导，然后设置`g.enabled=false`，停止正常组件更新。
- 选关、图鉴和设置由脚本直接打开；建造图先把金币设为999再建造豆包。
- 胜利图重新开第1关后直接设置`screen='win'`、`lives=8`，失败图直接设置`screen='lose'`、`lives=0`，没有走完整战斗。
- 脚本给`g.kills`赋值，但该版结算读取的是`defeated`和`earned`；波次也仍为初始0。因此第12页胜利图显示`0/4波`、`赶走0只夜间精怪`、`金币0`。

这类图可以用于内部检查界面和弹窗布局，不能被称为真实从开局到结束的操作记录。问题不在于使用浏览器截图，而在于用直接设置的状态代替了文档所描述的游玩过程。原记录中的“实机界面截图”应理解为引擎状态展示，不能据此认定已完成实机游玩验收；本次复盘纠正这一口径。

补正应重拍实际推进后的战斗与自然胜负结算，保留同局操作顺序、波次、金币、击退和耐久相符的原始证据。不能只改图片上的数字，不能把新版截图贴入旧版材料。图鉴或场景盘点若使用隔离测试进度，应明确记录来源，与完整一局的实际操作证据分别管理。

## 原检查为何漏掉

旧`qa_v101.py`主要检查页数、源码每页50行、Word插图数、标题数、版本号和渲染页数；旧材料说明也主要报告这些格式结果。它没有检查全部角色/地图/模式能否逐项对应图片，没有验证胜利图中的波次与击退数，也没有完整一局取图记录。

因此，“14页、17章、10张图、渲染正常”只说明文件形成了，不能支持“内容已完整覆盖”。主界面、设置、暂停和胜负页已有价值，但大量配图重复使用同一张未开波地图，信息覆盖明显不足。这是材料制作和复核流程应当承担并改进的遗漏；不能将其简单归因于审核方要求更多截图。

本地还保留原PDF、后改Word、排版终稿Word和多个渲染PDF。根目录PDF正文并未随最新Word同步，构成选错附件的风险。本轮无法认定线上实际发生了误传，但今后必须用最终上传文件的清单和摘要消除此类不确定性。
