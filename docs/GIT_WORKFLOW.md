## 提交原则

重要且已验证的变更应形成独立提交并同步到 GitHub，包括：

- 新玩法、关卡、系统或平台能力。
- 修复影响运行、数据或发布的问题。
- Cocos、抖音平台、包体或构建配置变更。
- 产品规则、架构、发布流程和测试标准变化。

临时实验、未完成代码、构建缓存和日志不提交。辅助文件继续放在 `G:\gptwork`。

## 标准步骤

1. `git fetch origin --prune`，阅读 `docs/PROJECT_STATUS.md` 和其他电脑的活动任务记录。
2. 在干净的最新 `main` 上创建本机任务分支，不在两台电脑上同时直接修改 `main`。
3. 创建独立工作记录，明确范围、涉及文件和验收条件，再开始改动。
4. 执行 TypeScript 检查和与改动风险相匹配的构建/测试。
5. 同步更新 README、项目状态、工作记录、产品、架构、测试、路线图或更新日志。
6. 检查差异后创建单一主题提交并推送任务分支。
7. 验收后将任务分支合并到 `main`，推送并确认本地、远端一致；另一台电脑随后以快进方式同步。

## 提交信息

建议采用 Conventional Commits：

- `feat:` 新功能
- `fix:` 缺陷修复
- `docs:` 文档
- `refactor:` 重构
- `test:` 测试
- `build:` 构建或平台配置
- `chore:` 维护工作

示例：`feat: add rewarded revive flow`

## 分支建议

- 稳定、已验证的版本保存在 `main`。
- 电脑 A 使用 `codex/pc-a/<topic>`，电脑 B 使用 `codex/pc-b/<topic>`。
- 两台电脑不得同时使用同一个任务分支，也不得修改同一任务记录。
- 功能分支只从最新 `origin/main` 创建，验收后合并。
- 不对共享分支使用强制推送。

完整的任务认领、交接和冲突处理流程见 [DEVELOPMENT_WORKFLOW.md](./DEVELOPMENT_WORKFLOW.md)。

## 安全规则

- 不提交账号密码、访问令牌、签名文件或私钥。
- 正式 App ID 可以进入平台构建配置；广告位 ID 是否提交由发布策略决定。
- 环境秘密使用本地或平台安全配置，并确保被 `.gitignore` 排除。
