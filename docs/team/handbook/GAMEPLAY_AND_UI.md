# 游戏制作经验

规范版本：2026-11-14.2。项目依据见[案例记录](../EXPERIENCE_REGISTER.md)，双机使用方法见[协作说明](../TWO_COMPUTER_WORKFLOW.md)。

## 核心体验先于内容规模

开工前明确玩家反复做的决定、决定的代价、结果如何显现，以及下一轮为什么值得继续。用具体动作表达，例如“看敌阵，调整站位与装备，在原场地看见调整结果”。只有系统名和功能清单时，先补这段体验。

优先完成一段包含决策、行动、反馈、结果、继续或重开的真实流程。人物、地图、商店、成就的扩展安排在该流程成立之后。已经有大量内容的项目，从真实卡点收拢体验，不为了重做首轮流程清除已有存档或强迫老玩家重走教学。

宗门经营案例收拢炼丹、开山、建丹房、放权、持续供丹闭关的过程说明：减少首轮并行目标，可以让已有系统形成能理解的因果链。该流程适用于修仙题材，其他游戏要建立自己的链条。

## 将自然感落实为统一的设计选择

本轮将“自然”具体理解为：题材、物体、动作、声音、文案与界面相互解释，玩家能理解正在发生的事。以下标准用于后续制作，尚未通过 Claude 作品同题对照验证。

每个游戏先确定代表性的场景、角色或物体，以及字体、色彩、材质、构图、动画的使用规则。参考图写明具体借鉴项，例如层级、人物比例或按钮材质；避免把多个参考的醒目部分无差别叠加。

建立三项最有辨识度的内容，并让它们在真实游戏中出现。灯塔、纸面经营记录、球场机关各有不同表达方式，不能把所有项目统一做成同一套深色面板与发光卡片。

制作时检查：

- 去掉标题后，画面是否仍能看出题材和主要玩法。
- 每个装饰、动画、音效是否服务于世界表达、信息辨识或动作反馈。
- 主次是否明确，关键内容能否被一眼找到。
- 删除重复面板、说明或装饰后，体验是否更清楚。
- 新加入的组件是否延续本游戏既有视觉规则。

若最初方向不成立，应调整场景构图、比例或流程，再扩展细节。增加纹理和粒子不能自动修复错误的物体表达。

## UI 要支持玩家当前的决定

先明确玩家当前要完成的任务，以及作决定必须看到的信息；按重要性、使用频率和出现时机取舍，去除重复说明，再建立视觉层级、安排布局，最后校准字号、间距和尺寸。不要先铺满全部功能、状态与规则，再靠缩字、扩大窗口或机械放大所有控件补救。

同屏建立明确的阅读顺序和操作轻重。常用任务及关键决定信息优先，辅助管理与低频详情适度弱化、按需展示；必要费用、重要缺项和高频操作不能为简洁而隐藏或绕路。用户限定只改排版、不改交互时，保留功能与操作流程。

已有装备、物品和角色美术承担识别，数量与必要状态辅助判断；逐项检查标签是否增加信息。避免给每个图形配一套重复文字，也不要把含义不明的动作全部改成无标签图标。用邻近、留白、对齐、对比和有限强调分组，不给每块内容都叠加厚边框、醒目底色、金字或大按钮。沿用美术也要控制视觉重量。

显示的装备与奖励必须能对应实际携带、拥有、预览或待获得状态，不能混在同一排暗示已经装配；详情关闭应回到实际进入上下文，保留原选择及筛选，不凭所在主界面硬跳另一个管理页。用真实部署、领取及返回操作核对这些含义。内部key与调试信息留在工具中。

交付前主动判断：第一眼重点是否明确，常用任务是否需要读大量文字，主操作是否易找，增减与删除是否易误触，费用和结果是否清楚，二级页面是否溢出截断。实际做过的画面与操作检查、真实手机和用户认可分别记录；脚本通过、内容放得下或按钮能点不代替体验判断。

设计规范由Agent内化并主动用于判断、自检，不把搜索结果或规范复述当作设计能力，也不等用户反复指出拥挤和主次问题才逐项删改。用户要求先思考、调研或暂不设计时，停在理解与判断，不继续修改原型。

## 先做组件和完整页面再铺开 UI

开始大范围 UI 修改前，形成一页能运行的组件样板，包含字体层级、语义色、按钮状态、图标、信息卡及关键数值；再组装一个完整主要页面，检查最小屏和极端内容。样板形成稳定基线后，扩展到其他页面。

已有用户确认的视觉基线优先复用。授权自主制作时，Agent 自行完成样板、实看与修订，按原定交付节点汇报；不因制作流程增加新的逐页确认要求。

每个项目明确：

| 项目 | 需要定义的内容 |
| --- | --- |
| 文字 | 字族、字号角色、字重、行距、长文和长名称处理 |
| 颜色 | 标题、正文、辅助、收益、风险、选中、不可用的语义 |
| 按钮 | 主次操作、默认、按下、选中、不可用及原因 |
| 图像 | 显示比例、可见轮廓、透明留白、视觉重心、文字安全区 |
| 布局 | 间距、对齐、分页或内部滚动、固定返回与主要操作 |
| 状态 | 初始、成长、满值、长数值、无资源、等待、失败 |

先核对项目实际预制体、设计分辨率、弹窗和字体控件规格，再选择适合内容密度的排版。参考界面尺寸相同，也不能直接套用其内容和控件密度。区分引擎设计单位、设备像素、屏幕密度、网页预览缩放和平台pt/dp，分别检查可见大小、有效触区、间距与误触；某个数字达标不能独立证明可读易点，桌面截图等比缩小也不能代替手机适配。

文字放不下时，先减重复、改结构、分页或进入详情。避免通过整体缩放、截断重要条件或不断缩字解决问题。检查真实文字边界与按钮内部安全区，而非仅检查控件外框。

同类弹窗统一内容底板、背景遮罩、返回和点击隔离。灯塔用户确认的“框内实色、框外半透”属于该游戏基线；其他游戏依据题材确定自己的窗口规则。

## 美术表达要与实际规则对应

机关、装备、增益和危险应有稳定的识别方式。高尔夫风车仅用旋转三角代替实体时，增加纹理仍难以辨认；恢复可识别轮廓和动作关系，才能传达机关身份。

图标与素材同时检查原尺寸和最终显示尺寸。素材等比展示；需要变长的按钮使用已定义保护边角的九宫格。检查非透明轮廓和视觉重心，不能只让 PNG 画布大小一致。

确定素材替换槽位、尺寸、锚点和拉伸规则，再批量生产。Cocos 等引擎保留所需元数据和可编辑场景结构，资源移动核对引用与 UUID。先用真实目标构建检验导入、字体和遮罩，避免最后迁移引擎时才发现语义差异。

借鉴其他项目时复用制作方法、结构经验与验收方法；资源来源、平台身份和存档命名空间按目标游戏分别核对。

## 选择需要影响真实过程并留下经历

选择的结果应进入后续规则，玩家能看出代价与收益，并在稍后辨认自己的影响。避免所有选项只是奖励数值不同，或者任何选项都能没有代价地获得全部收益。

经营游戏的人物要能记住共同经历。经理经营案例把身份约定、培养目标、实际出场、后续谈话连起来：承诺按真实比赛核对，未上场不能仅凭属性增长标为完成，挂牌也不能直接写成已转会。

文字游戏的片段应符合年龄、年代、身份和已经发生的事实。人生叙事案例用后续生活片段延续选择，避免把一个兴趣选项直接写成已经换工作或改变家庭关系。

验收时连续玩到后果显现。检查是否出现真实取舍、是否记得人物或事件、是否愿意换方案再试。结果无分量时先修规则和反馈，不用追加成就弹窗掩盖。

## 节奏同时检查等待与打断

记录新玩家首次有意义操作、一次核心循环、关键节点和重复操作所需的时间。动作游戏核对响应、前摇、命中、受伤、死亡与拾取；经营游戏核对推进、信息阅读、比赛观看与重复办理。

反馈要匹配事件的重要程度。普通事件合并到日志、收件箱或轻提示，真正需要决定时再暂停；失败时帮助玩家理解原因。音效、停顿、动画与震动一起调整，避免装饰反馈盖过敌人预警或必要信息。

多人同时攻击时，分别定位施法者、武器或弹体前端、实际受击者。贴身反馈可以跟随当前姿态的躯干或武器挂点，地面法术沿用其判定落区。只有战斗事件确认命中才播放命中反馈。角色拥挤时，依据屏幕上的实际占位错开名牌与血条。在同一段高密度交战中核对接触前、结算当拍和消退后的连续画面；可回放的项目另核对跳回同帧时的显示顺序。以上方法适用于需要读清战斗归属的场景，镜头、材质与显示时长由各游戏决定。

经理经营案例的普通回访没有加入频繁强制弹窗；策略征途案例的完整征途记录暴露大量重复操作。做出完整通关流程后，还要检查中后期是否机械、观战是否有无聊空档。

## 数值与广告价值要做同条件对照

按目标项目的相同输入、种子与策略对比不同方案，记录资源实际使用、完成时间、失败原因和玩家操作负担。模拟用于定位问题，再用真实客户端抽查。

策略征途案例的复盘显示，部分固定金粮奖励在后期失去用途；转向减少精力等待后，才在当时的配对样本中体现加速。后续用户仍认为力度不够，又继续调整。这说明奖励“到账”和“值得领取”是两个不同的验收问题。

免费流程应按本游戏目标保持完整可玩；可选广告提供能感受到的价值。不要复制另一游戏的奖励额度、敌人强度或次数，也不要用单个胜利样本承诺普遍收益。均值、异常种子与阶段差异一起检查。

降低升级打断频率或改变等级上限时，连同角色、区域、军械解锁与进化构筑检查可达性。用同种子、同输入策略对比选择次数、相邻作战间隔、成型时间、生存与失败原因，集中经验和旧进行中对局分别验证。等级上限、单次强化和回血数值保留为项目参数，不推广为其他游戏默认值。

## 可靠性和加载体验从第一版建立

保存、广告回调、暂停恢复、输入取消和重复点击属于体验基础。涉及奖励时，核对完成凭据、保存与领取的顺序，以及刷新、跨版本、旧页面和中断恢复。保存成功提示要有实际持久化依据。

不要将纯客户端无法保证的中断场景写成绝对保证。测试中的本地广告演示和真实宿主回调分别记录。

加载分成平台黑屏、包体下载、引擎启动、首屏、可交互与内容加载。尽早显示有用的游戏加载反馈，同时测量真正的首屏与可交互时间。游戏内 loading 不能证明平台黑屏已缩短；灯塔的“黑屏压至两秒内”是用户提出的目标，不能当成已经实现的结果或所有平台的统一预算。

处理首次加载过慢时，按以下顺序检查：

1. 先让加载反馈独立于重资源。首屏只带必要样式、文案和轻量背景预览，完整插画、引擎及非首屏内容随后准备；原图就绪再替换预览。未知总量显示等待，进度只取真实下载或准备状态。断网时标题、失败提示与重试按钮也要可见，不依赖按钮皮肤下载成功。
2. H5同时量FCP、文档load、主页可交互和宿主启动页消失。头部预载大图、脚本可能推迟load，即使文字早已绘制；检查瀑布图后，将不影响首屏的请求移至首屏绘制后。是否需要等load、宿主是否用它撤除启动页，应按平台实测决定，不能统一照搬，也不能用FCP代替平台等待。
3. 先统计实际产物中图片、音频、视频、脚本与数据的占比，再优化主要来源。优先减少重复与无用传输，尝试无损压缩；核对尺寸、透明通道、完整RGBA及色彩/方向元数据，并用目标运行时和实际HTTP类型验证加载与绘制。格式、扩展名和引擎引用的特殊处理只属于已验证项目，不作为跨游戏默认方案。
4. 同设备、同网络、同一入口对比新旧包，冷缓存与回访分别测，多轮报告中位数；同时报告包体、首屏反馈与完整可交互时间，避免把等待转进loading写成总加载时间同等缩短。最终上传ZIP独立解压复测，并将哈希、来源与设备边界留在游戏内记录。
5. 批量性能或解码探针报错时，先在未改基线上复现，再用游戏实际消费资源的API、真实绘制及有界内存复查。区分探针造成的资源压力与运行故障，保留失败证据，不靠忽略异常或移除资源获得通过。

按目标设备检查长时间运行、资源峰值和输入延迟；性能预算由具体项目确定。目标编译产物、真实引擎、浏览器与手机的结论分开，避免源代码行为正确但转译产物失败。

## 配置和存档保留可追踪来源

沿用项目已有原表和导出工具。可调规则、文本与资源引用按既有表结构管理，算法与技术协议留在代码。配置先核对 ID 分类、分隔符和字段解析，再导出并检查实际客户端所用版本。

跨项目不混用存档键、平台身份、广告位或密钥。改规则、删除内容或调整关卡时，明确旧档保留、迁移或重开方式，不静默重算已经发生的结果。

配置说明和检查日志放任务资料目录，保持实际配置目录紧凑。源码、原表、导出数据和资源的对应关系写清楚，便于另一台电脑重现。

## 交付需要画面和体验证据

交付分别给出以下结论，按改动范围选择必要验证：

| 结论 | 应有的依据 |
| --- | --- |
| 工程可运行 | 受影响的构建、配置与有意义的规则检查 |
| 界面可理解 | 最终构建在实际大小下的画面、关键状态与输入检查 |
| 流程有体验 | 连续试玩、卡点和修订；数值变化有必要的同条件对照 |
| 宿主可用 | 具体平台、版本、设备与真实功能的验收记录 |
| 交付版本一致 | 源码与配置来源、产物 SHA256、平台包号及实际绑定关系 |

自动检查通过数量不作为审美或好玩的分数。检查要能发现具体失败；纯文档和轻微可逆改动不新增与实现逐句重复的测试。

宣传截图选择实际玩法的不同代表场景。幸存者玩法案例应分别体现角色、图鉴、两类三选一、Boss 和战斗，避免六张都在展示相似特效。每张图说明一个真实特色，截图、录像、文案与当前实际包一致。

上传、绑定、提审、审核通过、版本生效、普通玩家可进入分别记录。本地完成后还要核对真正交付的包，避免旧包留在试玩入口。

## 每轮如何留下可复用经验

用[经验记录模板](../templates/LESSON_RECORD.md)记录有价值的新问题。重复出现且适用范围清楚时，更新目标项目规范；跨项目都适用的内容再汇入本文件。

通用规范保持精简且可执行，项目细节留在所属项目。当前规则写成单一结论，历史版本放在案例或变更记录中；用户新的明确要求及时替换旧要求，避免在同一规范顶部不断叠加互相冲突的段落。
